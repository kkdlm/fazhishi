# 内容鉴权改造方案（P1 · 暂缓实施）

> 状态：**未实施，方案已定，等开工**（2026-11-21 记）
> 触发条件：开始公开推广 / 真靠卡密收钱 / 发现有人扒走题库转发时 → 立刻启用
> 相关：`docs/公开仓库下的隐私边界方案.md`（那份管的是“用户数据别泄露”，这份管的是“内容别被白拿走”）

---

## 0. 一句话结论

现在 `app.html` 把全部背诵、题库、解析、精讲打包成 6.5MB 公开文件，会员判断只在前端 JS 里——**下载即得全部内容**，属于“锁在门上、钥匙挂门边”。改造方向：内容按章拆包放 Supabase 私有存储，凭登录身份发，非会员只拿到免费章节。

## 1. 现状事实（2026-11-21 线上 3.20.0 补丁 5）

| 项 | 现状 |
|---|---|
| 成品体积 | `法制史一图流.html` ≈ 6.5MB，含全部 points/items/quiz/解析/精讲 |
| 内容保护 | 无。任何人 `curl` 一次就拿全 |
| 会员门槛 | 前端 `isVip()` 判断，改本地 `S.vipUntil` 或直接读 HTML 都能绕过 |
| 免费额度 | 已服务端计数（`free_bk_take`），但“扒内容”完全绕过它 |
| 设备限制 | 已服务端 3 台 + 稳定指纹，同样绕不过“直接下载” |
| 卡密/邀请 | 已服务端化，有效 |

## 2. 免费边界（二选一，待拍板）

- **方案 A（全搬）**：非会员只能看「专题史 · 整合版」+「一图流原页」+ 每天 5 张背诵；断代史、精讲、背诵全文、题库、解析、时间轴全部服务端下发。
- **方案 B（部分搬，推荐起步）**：只把**题库 + 真题解析 + 精讲一本通全文**搬到服务端；背诵卡片、一图流仍留在包里。
  - 理由：真正值钱、最容易被转发的是题库和解析；背诵卡片体积大、拆分成本高、转发价值低。
  - 效果：风险下降约 80%，工作量约为 A 的一半。

> 默认按 **B 起步**，A 作为第二阶段。开工前由你确认一句即可。

## 3. 目标架构

```
App(壳 + 免费内容)  ──登录 token──▶  Supabase
                                   ├─ Storage：私有桶 content/（按章 .json，禁止匿名）
                                   ├─ RPC：get_chapter(p_chap) → 校验会员 → 返回数据（或短签名 URL）
                                   └─ 表：profiles / cards / free_usage …（已有）
```

- 内容包粒度：**按“章 / 专题”拆**（约 20–40 个包，单包 100–500KB 为宜）。
- 包结构（JSON，压缩后上传）：

```json
{ "v": "3.22", "chap": "xingfa-01", "title": "刑事·第一节 罪名",
  "items": [ …原文/要点… ], "quiz": [ …题干/选项/解析… ], "parse": "…精讲全文…" }
```

- 鉴权三选一（推荐第 2 条）：
  1. Storage 桶 + RLS 策略（`auth.uid()` 且会员才 select）→ 前端直连取；
  2. **RPC `get_chapter()`（security definer，内部判 `is_vip()` / `pro_until`）→ 返回 JSON**，前端不接触桶；
  3. Edge Function 签发 5 分钟短签名 URL。
- 会员判定统一走服务端：`pro_until > now() and not banned`。

## 4. 实施步骤

1. **内容导出**：`build/export_content.py` 从 `build/app_fz.html` 的数据源（`PTS/QUIZ/讲义` 等常量）导出为按章 JSON，写 `content/*.json` + `content/index.json`（章目录、版本、校验和）。
2. **建桶与函数**：`docs/content_auth.sql` —— `storage.buckets` 建私有桶 `content`；`get_chapter(p_chap text)`、`content_index()`、`is_vip()`（已有可复用 `pro_until` 判断）。
3. **上传链路**：`build/upload_content.py`（service_role 或 Management API 上传），产物不入公开仓库。
4. **App 侧**：新增 `CHAP` 缓存层
   - `loadChapter(chap)`：先查本地缓存（IndexedDB，key=chap+版本）→ 未命中走 RPC → 落缓存
   - 渲染入口按章懒加载；无网络时用缓存，缓存也没有则显示「联网后加载」占位
   - 会员态变化（到期/封禁）时清会员章缓存
5. **构建改造**：`inject_fz.py` 只注入壳 + 免费内容 + 章目录；`release.yml` 增加一次内容包发布（版本号对齐）。
6. **降级与兼容**：保留一条 `/content-fallback/*.json` 公开发布路径（仅在 Supabase 不可用时手动开启），避免服务挂掉全站打不开。
7. **验收**（见第 6 节）。

## 5. 风险与代价

| 风险 | 说明 | 缓解 |
|---|---|---|
| 首启/切章变慢 | 不再是本地单文件 | 缓存 + 预取相邻章 + 骨架屏 |
| 断网不可用 | 会员章需联网首取 | IndexedDB 缓存 + 离线提示 |
| 服务端故障 | 内容取不到 | 公开降级包（开关手动开） |
| 缓存不一致 | 内容更新后取旧包 | 包内带版本号，`index.json` 校验和比对 |
| 维护成本 | 多一套导出/上传/校验链 | 写成脚本 + CI 一步完成 |
| 体积分摊 | 单包 100–500KB × 按需 | 比 6.5MB 全量更新更省流量 |

## 6. 验收清单（做完逐条打勾）

- [ ] 匿名 `curl` 任一会员章包 → 404 / 401
- [ ] 非会员 token 调 `get_chapter('xingfa-01')` → 拒绝且提示明确
- [ ] 会员 token → 正常返回，且与 App 渲染一致
- [ ] 断网二次打开已看过的章 → 正常显示（缓存命中）
- [ ] 断网打开未看过的会员章 → 明确提示，不白屏
- [ ] 到期/封禁后 → 会员章立刻不可取（清缓存）
- [ ] 发布包内 `grep` 不到会员章的题干/解析原文
- [ ] 390×844 dpr3 无溢出、`pageerror 0`
- [ ] 版本号与 `version.json`、内容索引版本一致

## 7. 分版实施计划（建议）

| 版本 | 内容 |
|---|---|
| v3.22.0 | 导出脚本 + 建桶/函数 + 题库解析搬服务端（方案 B 前半）+ 缓存层 |
| v3.23.0 | 精讲全文搬服务端 + 后台新增「内容包」页（章目录、更新、校验） |
| v3.24.0 | 若走方案 A：背诵/断代史/时间轴按章服务端化 + 免费边界收敛 |

每版都保留旧逻辑回退开关（`CONTENT_MODE='local'|'remote'`），出问题一个开关切回单文件模式。

## 8. 回滚方案

- `CONTENT_MODE='local'`：App 回到打包全量模式（旧版 `app.html` 仍在 CDN，可一键指回）。
- 内容包发布失败：CI 校验和不一致即中止，保留上一版包。
- 数据库函数异常：回退到旧 RPC（`vip_cards.sql` 全量幂等可重跑）。

## 9. 为什么现在不做

- 当前用户规模是“自己 + 同学几十人”，扒内容的动机低；
- 一次性改动跨构建、存储、鉴权、缓存四层，容错率要求高（你对内容错误/逻辑漏洞零容忍）；
- 现有 P2（免费额度、设备指纹）已完成，先把这套跑稳再动大手术更安全。

## 10. 待你拍板的两件事（开工前）
