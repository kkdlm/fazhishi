# 版本号规则（自 4.0.0 起严格执行）

三段：`主.次.补丁`，**每段一位数字（0–9）**。

| 段 | 什么时候加 | 满了怎么办 |
|---|---|---|
| 补丁 | 只修 bug、文案、小优化，不改功能面 | 补丁满 9（3.x.9）再要修 → 进次版本 `3.(x+1).0` |
| 次版本 | 加功能、但用法不变（用户无需重新学） | 次版本满 9（3.9.y）再要加功能 → 进主版本 `4.0.0` |
| 主版本 | 结构性变化（内容分发方式、账号体系重做、UI 重构） | — |

所以 **3.9.9 之后就是 4.0.0**，不会出现 `3.10` / `3.22` 这种。

## 实际写法

- 正文：`const VER='4.0.0'; const PATCH='0';`（补丁是同一版本内的序号，从 0 起）
- 外壳：`var VER='4.0.0-p0'`
- Service Worker：`const CACHE='app-4.0.0-p0'`
- `version.json`：`{"version":"4.0.0","patch":0,"s":<字节数>}`
- 用户看到的版本记录：`v4.0.0`，补丁 >0 时写「补丁 N」

## 自动校验

`.github/workflows/release.yml` 第一步就校验：版本号必须匹配 `^[0-9]\.[0-9]\.[0-9]$`，补丁号必须匹配 `^[0-9]$`；不匹配直接失败，越界版本不会上线。后续步骤再核对壳 / 正文 / sw 三处版本串一致。

## 历史说明

`3.17.0`–`3.22.0` 是早期按“次版本两位”排的旧编号（`3.22.0` 已越界，仅在线上存在过几十分钟），已归档不再改动；**从 4.0.0 起严格一位**，所以版本记录里会看到 3.21.0 之后跳到 4.0.0，这是归位，不是丢版本。
